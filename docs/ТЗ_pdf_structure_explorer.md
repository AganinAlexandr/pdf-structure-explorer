# Техническое задание

## 1. Назначение проекта

Создать веб-приложение для загрузки, постраничного разбора, визуализации и инспекции структурных элементов PDF-файлов. Приложение должно позволять пользователю видеть состав страницы PDF и получать подробную информацию по каждому элементу при наведении курсора.

Рабочее название проекта: `pdf-structure-explorer`.

## 2. Цель

Обеспечить удобный инструмент для анализа внутренней структуры PDF-документов:
- текстовых блоков и символов;
- рамок, линий, прямоугольников и других векторных примитивов;
- изображений;
- слоев отображения и визуальной глубины элементов;
- языков текстового содержимого, включая выявление битых кодировок;
- строгой иерархии элементов с обязательными количественными признаками и агрегированием по страницам, слоям, языкам и группам элементов.

## 3. Контекст создания проекта

При запуске проекта использовать целевую инфраструктуру:
- код проекта хранить в `E:/repos/<project-name>`;
- общие данные и справочники хранить в `E:/commons/`;
- результаты работы, временные выгрузки и экспорт хранить в `E:/output/<project-name>/`.

Минимальные файлы проекта:
- `.gitignore`
- `.env.example`
- `.env`
- `README.md`

Минимальные переменные окружения:

```ini
COMMONS_ROOT=E:/commons
OUTPUT_ROOT=E:/output/pdf-structure-explorer
UPLOAD_ROOT=E:/output/pdf-structure-explorer/uploads
CACHE_ROOT=E:/output/pdf-structure-explorer/cache
```

## 4. Рекомендуемая техническая база

Рекомендуемый стек для реализации:
- frontend: `React + TypeScript + Vite`;
- backend: `Python + FastAPI`;
- PDF-разбор: `PyMuPDF` как основная библиотека;
- детектирование языков: `langdetect` или аналог с дообработкой;
- хранение метаданных сессий: `SQLite`;
- клиентская визуализация: `Canvas/SVG overlays`.

Обоснование выбора:
- `PyMuPDF` хорошо извлекает текстовые блоки, span-элементы, изображения, векторные примитивы и координаты;
- `FastAPI` удобен для API, фоновых задач и выдачи JSON/preview;
- `React` удобен для сложного интерактивного интерфейса инспектора.

Формат первого этапа:
- приложение реализуется как локальное однопользовательское решение;
- backend и frontend запускаются локально на компьютере пользователя;
- требования многопользовательской работы, серверного развертывания и общей авторизации не входят в первый этап.

## 5. Основные сценарии использования

1. Пользователь загружает PDF-файл перетаскиванием или через диалог выбора файла.
2. Система разбирает PDF постранично и строит структурную модель документа.
3. Пользователь открывает страницу документа и видит визуальное представление PDF.
4. При наведении курсора на элемент страницы справа отображается карточка элемента.
5. Пользователь включает и отключает отображение отдельных типов элементов и слоев.
6. Пользователь включает цветовую подсветку языков текста.
7. Пользователь фильтрует отображение текста по языкам.
8. Битые кодировки отображаются как отдельная категория и подсвечиваются красным фоном.
9. Пользователь выбирает в правой панели верхнюю группу элементов, например `рамки`, и слева на странице остаются только элементы этой группы.
10. Пользователь просматривает справа список всех элементов выбранной группы с их параметрами и количественными признаками.

## 6. Функциональные требования

### 6.1. Загрузка файлов

Система должна:
- поддерживать загрузку PDF через drag-and-drop;
- поддерживать загрузку PDF через кнопку выбора файла из каталогов компьютера;
- валидировать тип файла;
- отображать состояние загрузки и разбора;
- поддерживать загрузку как минимум одного файла за раз в MVP;
- предусмотреть возможность расширения до пакетной загрузки.

### 6.2. Разбор PDF

Для каждой страницы система должна извлекать:
- текстовые блоки;
- строки;
- spans;
- при необходимости отдельные символы;
- координаты каждого элемента;
- параметры шрифта: имя, размер, начертание, цвет;
- информацию о повороте текста;
- рамки, линии, прямоугольники и другие векторные объекты;
- изображения с координатами, размерами и ссылкой на превью;
- таблицы как отдельные составные сущности;
- порядок отрисовки элементов;
- сведения о PDF-слоях, если они присутствуют в документе как OCG/Optional Content Groups.

Система должна строить строгую иерархию представления данных:
- `Document -> Page -> Layer -> Group -> Subtype -> Element`;
- для текстовых элементов дополнительно должен поддерживаться разрез `Language`, где это применимо;
- для агрегатов должна поддерживаться навигация от верхнего уровня к нижнему без потери связи с исходной страницей и координатами.

Минимальные верхние группы элементов для MVP:
- `text`;
- `lines`;
- `frames`;
- `images`;
- `tables`;
- `other_vector` при необходимости.

Система должна различать как минимум:
- линии как отдельные линейные объекты;
- рамки как замкнутые прямоугольные или контурные объекты;
- изображения как растровые или встроенные графические объекты;
- таблицы как отдельные составные объекты, связанные с ячейками, текстом, линиями и рамками;
- текст как текстовые элементы с возможностью детализации до span и при необходимости до символа.

Требования к таблицам в MVP:
- таблицы должны выделяться как отдельная сущность верхнего уровня, а не только как набор текста и линий;
- для каждой таблицы должна сохраняться связь с вложенными элементами страницы;
- таблица должна иметь собственный идентификатор, координаты, габариты и количественные признаки;
- по возможности должны выделяться как минимум границы таблицы, число строк, число столбцов и число ячеек;
- если часть структуры таблицы не распознана уверенно, система должна сохранять признак частичной уверенности, но не скрывать сам факт наличия таблицы.

Если полноценные PDF-слои отсутствуют, система должна формировать логические слои визуализации:
- текст;
- векторная графика;
- изображения;
- дополнительные служебные слои интерфейса.

Требования к логическим слоям:
- логические слои должны использоваться только как упрощенная модель, если в PDF нет нативных слоев;
- количество логических слоев в интерфейсе должно быть ограничено и составлять не более 3-5 пользовательских категорий;
- набор логических слоев должен быть простым и понятным пользователю без технической перегрузки;
- в панели слоев и в режиме просмотра должен явно отображаться индикатор, что показаны именно логические слои, а не нативные слои PDF.

Для каждого элемента система должна сохранять обязательные количественные признаки, где они применимы:
- координаты `x1`, `y1`, `x2`, `y2`;
- ширина;
- высота;
- площадь ограничивающего прямоугольника;
- порядок отрисовки;
- нормализованный уровень глубины;
- номер страницы;
- идентификатор слоя;
- идентификатор верхней группы;
- идентификатор подтипа.

Дополнительные количественные признаки по типам:
- для текста: длина строки, количество символов, размер шрифта;
- для линий: длина, толщина линии;
- для рамок: ширина контура, периметр, площадь рамки;
- для изображений: ширина, высота, площадь, размер бинарного объекта при наличии;
- для таблиц: число строк, число столбцов, число ячеек, площадь таблицы, число вложенных текстовых элементов.

### 6.3. Визуализация страницы

Экран приложения должен быть разделен на области:
- слева узкая вертикальная колонка миниатюр страниц с отдельной прокруткой;
- рядом основная область просмотра выбранной страницы PDF;
- в основной области должен быть ползунок масштабирования;
- справа информационная панель по элементу под курсором;
- справа отдельная панель слоев;
- справа отдельная панель языков текста.

Требования к просмотру страницы:
- отображать страницу PDF максимально близко к оригиналу;
- поверх страницы накладывать интерактивные области элементов;
- при наведении подсвечивать границы элемента;
- при клике фиксировать выбранный элемент;
- поддерживать прокрутку многостраничного документа;
- обеспечивать переключение между страницами через миниатюры;
- поддерживать режим показа только выбранной верхней группы элементов;
- поддерживать режим показа только выбранного слоя;
- поддерживать режим показа только выбранного языка для текстовых элементов.

Система должна поддерживать несколько видов курсора для работы в области страницы:
- стандартный указатель;
- точный перекрестный курсор;
- тонкий прицельный курсор для мелких элементов;
- режим выделения элемента с усиленной подсветкой активной области.

Переключение вида курсора должно быть доступно пользователю через интерфейс без перезагрузки страницы.

### 6.4. Информация по элементу

При наведении или выборе элемента справа должна показываться информация:

Для текста:
- тип элемента;
- страница;
- координаты;
- текстовое содержимое;
- язык;
- признак битой кодировки;
- шрифт, размер, цвет;
- угол поворота;
- слой;
- глубина отрисовки.

Для линий и рамок:
- тип объекта;
- страница;
- координаты;
- толщина линии;
- цвет;
- тип контура;
- слой;
- глубина отрисовки.

Для изображений:
- тип объекта;
- страница;
- координаты;
- размеры;
- формат или внутренний тип;
- цветовое пространство при наличии;
- слой;
- глубина отрисовки;
- миниатюра изображения.

Для таблиц:
- тип объекта;
- страница;
- координаты;
- ширина и высота;
- число строк;
- число столбцов;
- число ячеек;
- число вложенных текстовых элементов;
- слой;
- глубина отрисовки;
- признак уверенности или частичной уверенности распознавания структуры.

Для всех типов элементов система должна уметь показывать не только карточку одного элемента, но и список элементов выбранной верхней группы с их основными параметрами и количественными признаками.

При выборе верхней группы справа система должна:
- показывать список элементов этой группы;
- показывать количественные итоги по этой группе;
- позволять переходить из списка к конкретному элементу на странице;
- синхронно фильтровать левую область просмотра так, чтобы на странице оставались только элементы выбранной группы.

### 6.5. Слои и глубина

Система должна:
- отображать список слоев в отдельной панели;
- позволять включать и отключать видимость каждого слоя;
- визуально кодировать глубину элементов цветом от светлого к темному;
- обеспечивать режим просмотра только выбранных слоев;
- обеспечивать режим исключения выбранных слоев;
- поддерживать легенду цветов глубины.

Примечание:
- если в PDF нет настоящих слоев, глубина должна определяться порядком отрисовки элементов на странице;
- чем позже элемент нарисован в PDF, тем он считается визуально ближе к пользователю.
- если используются логические слои, система должна ограничивать их число несколькими крупными категориями, чтобы панель слоев оставалась читаемой;
- если используются логические слои, рядом с названием панели или в легенде должен отображаться явный маркер `Логические слои`.

### 6.6. Языки и битые кодировки

Система должна:
- определять перечень языков, присутствующих в текстовой части документа;
- показывать этот перечень в отдельной панели;
- позволять включать и отключать отображение текста по выбранным языкам;
- поддерживать цветовую подсветку текста по языкам;
- подсвечивать битые кодировки красным фоном;
- позволять включать режим отображения только битых кодировок;
- показывать количество фрагментов по каждому языку.

Правила для MVP:
- русский и английский должны определяться как отдельные категории;
- битые кодировки должны определяться как отдельная категория `broken_encoding`;
- текст, не прошедший уверенную классификацию, допускается относить к категории `unknown`.

### 6.7. Фильтрация и режимы просмотра

Система должна поддерживать фильтры:
- по страницам;
- по типу элементов;
- по верхним группам элементов;
- по подтипам элементов;
- по слоям;
- по языкам;
- по битым кодировкам;
- по наличию изображений;
- по наличию векторной графики.

Система должна поддерживать агрегированные представления:
- по документу в целом;
- по каждой странице;
- по каждому слою;
- по каждому языку для текстовых элементов;
- по каждой верхней группе элементов;
- по сочетаниям `страница + группа`, `страница + слой`, `страница + язык`, где это применимо.

Для каждого такого представления должны быть доступны количественные показатели:
- число элементов;
- суммарная площадь покрытия страницы элементами группы, где применимо;
- суммарная длина линий, где применимо;
- число текстовых фрагментов и символов;
- число изображений;
- число таблиц;
- число ячеек таблиц;
- число элементов с битой кодировкой.

### 6.8. Экспорт данных

Система должна обеспечивать выгрузку всех данных по элементам файла во внешний файл или набор файлов для последующей загрузки в Power Query и экспорта в Excel.

Требования к экспорту MVP:
- экспорт должен быть доступен из интерфейса для обработанного PDF;
- экспорт должен содержать все элементы документа, а не только текущую страницу;
- экспорт должен сохранять строгую иерархию и связи между сущностями через идентификаторы;
- экспорт должен быть пригоден для загрузки в Power Query без ручной переработки структуры;
- кодировка текстовых файлов экспорта должна быть `UTF-8`.

Рекомендуемый формат экспорта MVP:
- набор `CSV`-файлов нормализованной структуры;
- один служебный `JSON`-manifest с описанием документа и связей выгрузки.

Минимальный состав экспорта:
- `documents.csv`;
- `pages.csv`;
- `layers.csv`;
- `element_groups.csv`;
- `elements.csv`;
- `text_segments.csv`;
- `images.csv`;
- `tables.csv`;
- `language_summary.csv`;
- `group_summary.csv`;
- `page_summary.csv`;
- `manifest.json`.

Экспортируемые таблицы должны включать:
- идентификаторы связей между документом, страницей, слоем, группой, подтипом и элементом;
- все обязательные количественные признаки элементов;
- языковые признаки там, где они применимы;
- признаки битой кодировки;
- агрегаты по страницам, слоям, языкам и группам.

## 7. Пользовательский интерфейс

### 7.1. Компоновка

Предлагаемая компоновка:
- левая колонка `Thumbnails`;
- центральная колонка `Page Viewer`;
- правая колонка `Inspector`.

Правая колонка должна содержать вкладки или отдельные секции:
- `Элемент`;
- `Слои`;
- `Языки`.

В правой колонке также должна быть отдельная секция или субокно `Группы элементов`, в котором:
- показывается список верхних групп элементов;
- показывается количество элементов в каждой группе;
- показываются дополнительные агрегаты по выбранной странице и по документу;
- выбор группы немедленно фильтрует отображение страницы слева;
- выбор элемента из списка группы переводит фокус к соответствующему объекту на странице.

Если документ отображается через логические слои, в секции `Слои` должен быть заметный статус или бейдж `Логические слои`, поясняющий, что это не исходные PDF-слои документа.

### 7.2. Цветовые режимы

Система должна поддерживать режимы подсветки:
- по типу элемента;
- по глубине;
- по языку;
- по битым кодировкам.

Рекомендуемые правила:
- русский: один цвет;
- английский: второй цвет;
- `unknown`: нейтральный цвет;
- `broken_encoding`: красный фон;
- глубина: градиент от светлого к темному.

### 7.3. UX-требования

Интерфейс должен:
- быть пригодным для работы на десктопе;
- корректно работать при ширине окна от 1440 px;
- не терять отзывчивость на документах средней сложности;
- показывать понятные статусы разбора и ошибок;
- позволять быстро снять все фильтры и вернуться к исходному виду;
- позволять быстро переключать режим курсора;
- позволять быстро переключаться между режимом одиночного инспектора и режимом группового списка элементов.

## 8. API и модель данных

### 8.1. Основные сущности

Минимальные сущности:
- `Document`
- `Page`
- `Element`
- `ElementGroup`
- `ElementSubtype`
- `Layer`
- `LanguageSegment`
- `ImageAsset`
- `TableAsset`
- `PageSummary`
- `GroupSummary`
- `LanguageSummary`
- `ExportPackage`

### 8.2. Иерархия и связи

Базовая иерархия данных должна быть следующей:

```text
Document
  -> Page
    -> Layer
      -> ElementGroup
        -> ElementSubtype
          -> Element
```

Дополнительные аналитические разрезы:
- `Language` для текстовых элементов;
- `DrawOrder/Depth` для всех отображаемых элементов;
- `SelectionState` для интерфейсной фильтрации и инспекции.

Все сущности должны иметь стабильные идентификаторы для связи в API, UI и экспортных таблицах.

## 9. Нефункциональные требования

Система должна:
- обрабатывать PDF объемом не менее 300 страниц в режиме поэтапной загрузки данных;
- поддерживать постраничный lazy loading;
- не блокировать интерфейс на время полного разбора всего документа;
- логировать ошибки парсинга;
- сохранять промежуточные результаты разбора в кэш;
- обеспечивать повторное открытие недавно обработанного файла быстрее первичного разбора;
- обеспечивать экспорт полного набора данных без потери связей между сущностями;
- формировать экспортные таблицы, стабильно открываемые в Power Query.

## 10. Ограничения и допущения

- Первый этап реализуется как локальное однопользовательское приложение.
- MVP ориентирован на PDF без OCR-распознавания текста в растровых сканах.
- Если страница является сканом без текстового слоя, текстовые данные могут отсутствовать.
- OCR можно рассматривать как этап 2.
- Таблицы в MVP должны выделяться как отдельная сущность, даже если они вычисляются на основе текста, линий и рамок.
- При неполном распознавании структуры таблицы система должна сохранять таблицу как сущность с признаком частичной уверенности.

## 11. Этапы реализации

### Этап 1. MVP

- загрузка PDF;
- постраничный разбор;
- просмотр страницы;
- миниатюры страниц;
- инспектор элемента;
- список верхних групп элементов с количествами;
- фильтрация страницы по верхней группе элементов;
- слои по типам элементов;
- глубина по порядку отрисовки;
- выделение таблиц как отдельной сущности;
- определение языков `ru`, `en`, `unknown`, `broken_encoding`;
- фильтрация и подсветка;
- несколько режимов курсора;
- экспорт полной структурной модели в CSV + JSON manifest для Power Query/Excel.

### Этап 2. Расширение

- пакетная загрузка файлов;
- OCR для сканов;
- поиск по тексту;
- сравнение двух PDF по структурным различиям.

## 12. Критерии приемки

Система считается принятой для MVP, если:
- PDF загружается drag-and-drop и через выбор файла;
- документ открывается постранично;
- пользователь видит миниатюры страниц слева;
- пользователь видит основную страницу и может менять масштаб;
- при наведении на текст, линию или изображение справа показываются свойства элемента;
- таблицы выделяются как отдельная сущность и доступны в общей иерархии элементов;
- таблицы можно выбрать через правую панель групп элементов так же, как текст, линии, рамки и изображения;
- в правой части доступен список верхних групп элементов с количественными показателями;
- при выборе группы, например `рамки`, слева остаются только элементы этой группы;
- в режиме группы справа показывается перечень всех элементов выбранной группы и их параметры;
- можно скрывать и показывать слои;
- число логических слоев при отсутствии нативных PDF-слоев ограничено несколькими понятными категориями;
- при использовании логических слоев интерфейс явно сообщает, что это логические, а не нативные PDF-слои;
- работает цветовая визуализация глубины;
- система показывает список языков текста;
- можно фильтровать текст по языкам;
- для элементов доступны обязательные количественные признаки и связи с page/layer/group/language, где применимо;
- для таблиц доступны количественные признаки как минимум по строкам, столбцам и ячейкам;
- доступен экспорт полного набора данных документа в формат, пригодный для Power Query/Excel;
- битые кодировки выделяются красным;
- пользователь может выбрать один из нескольких видов курсора для более точного указания элементов;
- приложение стабильно работает на тестовом наборе PDF.

## 13. Открытые вопросы

Перед стартом разработки желательно зафиксировать:
- нужен ли OCR в первой версии;
- нужен ли режим сравнения двух PDF;
- нужен ли экспорт сразу в `XLSX`, или достаточно `CSV + JSON manifest` для загрузки через Power Query.
